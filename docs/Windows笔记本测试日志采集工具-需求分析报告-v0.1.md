## 1 文档说明


### 1.1 编写目的

本报告面向“Windows 笔记本测试日志采集工具”的产品定义阶段，回答三个问题：测试现场到底需要哪些日志与系统信息、为什么需要、工具应以什么形态把这些信息交付出去。报告只做需求分析，不包含实现方案与代码。

适用读者：产品与项目负责人、测试负责人、研发与驱动工程师（日志消费方）、IT 与信息安全（合规审核）。


### 1.2 前提假设

以下假设决定了报告的范围。若某项不成立，对应章节需要调整。

**表 1-1 前提假设**

| 编号 | 假设 | 若不成立的影响 |
| --- | --- | --- |
| A1 | 测试对象是笔记本整机（硬件、固件、驱动、预装系统），而非单一应用软件 | 第 4 章的重心要从“应用日志”转向“整机状态”，采集项差异约 50% |
| A2 | 使用者是测试执行人员，多数不具备系统调试经验 | 若使用者是研发，可去掉向导、简化表单，但工具必要性下降 |
| A3 | 场景以研发与试产阶段为主（EVT/DVT/PVT/回归），非产线大批量 | 若含产线，需增加无界面批量、并发上传、机架式管理等需求 |
| A4 | 交付形态为免安装可执行工具，离线可用 | 若允许安装服务，崩溃自动采集与常驻监控可实现得更彻底 |
| A5 | 目标系统为 Windows 10 / 11，中英文系统混用 | 若含 Windows 7/8 或国产化系统，需重做兼容性章节 |
| A6 | 采集结果供公司内部研发定位，存在数据分级与合规约束 | 若可出境或对外共享，第 8 章的脱敏要求需大幅加强 |


### 1.3 术语

**表 1-2 术语表**

| 术语 | 含义 |
| --- | --- |
| SN | 设备序列号（Serial Number），用于把日志包绑定到具体样机 |
| EC | 嵌入式控制器（Embedded Controller），笔记本的电源、风扇、键盘、电池管理通常由其控制 |
| BSOD / BugCheck | 蓝屏及其错误码，例如 0x9F、0x133、0x124 |
| TDR | 显示驱动超时恢复（Timeout Detection and Recovery），表现为短暂黑屏或花屏 |
| WHEA | Windows 硬件错误架构，记录 CPU、内存、PCIe 的硬件级错误 |
| Modern Standby | 现代待机（S0ix），新型笔记本的主流待机方式，功耗与唤醒问题高发 |
| Dump | 内存转储文件，蓝屏时由系统生成，是定位内核态问题的关键证据 |
| WER | Windows 错误报告（Windows Error Reporting），用户态与应用崩溃的主要来源 |
| EVTX | Windows 事件日志的原始文件格式 |
| ETW | Windows 事件跟踪，用于细粒度性能与调度分析（WPR/xperf） |
| SMART | 磁盘自我监测与报告技术，含通电时间、写入量、温度、坏块等 |
| EDID | 显示器身份与能力数据，含面板型号与支持的分辨率、刷新率 |
| P0 / P1 / P2 | 优先级：P0 必须、P1 重要、P2 增强 |
| 档位 | 采集深度预设：快速 / 标准 / 深度，对应不同的耗时与体积 |
| 上会话 | 问题发生的那一次开机会话（相对于当前正在运行的会话） |


## 2 背景与问题定义


### 2.1 现状与痛点

笔记本整机测试中，绝大多数问题的定位成本不在“修”，而在“还原现场”。目前常见做法是测试人员凭经验手工执行若干命令、截图、拷贝日志，再由研发反复追问补充材料。主要痛点如下。

- 现场信息易失。事件日志按大小滚动覆盖，蓝屏转储可能被后续崩溃冲掉，WER 队列会被清理；一次偶发问题往往只有一次采集机会。
- 口径不统一。每个人抓的东西不一样，有人只截了蓝屏画面，有人拷了 3 GB 全量日志，研发既缺关键项又要从海量数据里翻找。
- 门槛偏高。需要熟悉事件查看器、powercfg、perfmon、驱动枚举等操作，测试人员培训成本高、执行易漏项。
- 缺少上下文。只有日志没有机型、BIOS 版本、测试用例和现象描述，研发无法把日志和具体批次、具体场景关联起来。
- 往返成本高。研发追问 → 测试补采 → 研发再追问，一个问题平均多耗 1–3 个工作日，且样机可能已经流转。
- 合规风险。手工打包容易把账号、Wi-Fi 密码、文档路径等个人信息带出去，缺少统一的脱敏与留痕。


### 2.2 工具定位

一句话定位：把“问题现场”标准化地冻结成一个可交付、可追溯、可被研发直接消费的数据包。

三个关键词。一键：降低执行门槛，让不会命令行的测试人员也能采全。标准：所有人采同一套内容、同一套命名、同一套结构，研发拿到任何一台机器的包都能按同样路径找到东西。可追溯：包内明确记录采了什么、缺了什么、谁在什么机器上、什么时间采的。


### 2.3 非目标（本期明确不做）

- 不做自动根因诊断与结论输出。工具给出事实与线索，不替代研发判断；自动标记（如“检测到 3 次 WHEA 硬件错误”）属于摘要范畴，不是诊断。
- 不做远程控制与被测机以外的数据采集。
- 不做日志的长期存储平台。工具只负责“产生标准包”，归档与检索属于平台侧（二期可对接）。
- 不做性能测试工具本身。只做问题发生时的状态快照与短时采样。
- 不修改系统配置、不安装驱动、不清空日志、不自动重启。


### 2.4 成功度量

**表 2-1 成功度量**

| 度量项 | 现状（估） | 目标 | 测量方式 |
| --- | --- | --- | --- |
| 单次采集耗时（标准档） | 20–60 分钟（手工） | ≤ 5 分钟 | 工具内计时 |
| 研发首次拿到包即可定位的比例 | 约 40% | ≥ 80% | 抽取 50 个历史问题回归验证 |
| 因材料不全导致的往返次数 | 平均 2–3 次 | ≤ 1 次 | 工单统计 |
| 关键项缺失率（P0 采集项） | 不可控 | ≤ 1% | 包内 manifest 统计 |
| 测试人员上手成本 | 需 1 小时培训 | 无需培训，3 次点击完成 | 可用性测试 |
| 单包体积（标准档） | 0.5–3 GB 不等 | ≤ 200 MB | 实测 |


## 3 用户与使用场景


### 3.1 角色

**表 3-1 角色与诉求**

| 角色 | 核心诉求 | 使用频率 |
| --- | --- | --- |
| 测试执行人员 | 点一下就能采全，不用记命令；采完知道成没成功、缺了什么 | 每天多次 |
| 测试负责人 | 统一口径、可统计；能按机型/用例追溯采集质量 | 每周 |
| 研发 / 驱动工程师 | 拿到包能快速找到时间线、崩溃原因、驱动与硬件信息 | 每天（消费方） |
| IT / 实验室管理 | 不破坏测试环境、不引入安全风险、可批量部署 | 每批次 |
| 信息安全 / 合规 | 个人信息不外泄、有告知与授权、有审计记录 | 评审节点 |


### 3.2 典型场景

**表 3-2 使用场景**

| 编号 | 场景 | 触发时机 | 关键要求 |
| --- | --- | --- | --- |
| S1 | 功能/兼容测试中发现异常，系统仍可用 | 发现问题当场 | 快速完成，不打断测试节奏；表单字段少 |
| S2 | 蓝屏、黑屏、自动重启、死机 | 重启进入系统后 | 必须能取到上一次会话的转储与崩溃前事件，时间窗自动前移 |
| S3 | 卡顿、掉帧、性能不达标 | 跑完性能用例后 | 含短时性能采样与 Top 进程；需说明采集本身对性能的影响 |
| S4 | 发热、风扇狂转、降频 | 负载运行中或结束后 | 含温度、风扇、降频事件与电源策略 |
| S5 | 续航不达标、充电异常、掉电快 | 放电或充电过程中 | 含电池报告、能耗报告、适配器识别状态 |
| S6 | Wi-Fi/蓝牙掉线、连不上、速率低 | 问题发生后 | 含无线历史报告与连接时间线 |
| S7 | 老化/长稳测试夜间运行后异常 | 次日早晨 | 支持定时或触发式采集，无需人工值守 |
| S8 | 同批次多台机器复现同一问题 | 批量 | 支持批量执行与统一命名，便于横向对比 |


### 3.3 一次完整使用流程

1. 测试人员发现问题，打开工具（若为免安装，双击即用）。
2. 工具自动预填机器 SN、机型、系统版本、当前时间。
3. 选择场景模板（如“蓝屏/死机”），档位默认标准。
4. 填写少量必填项：用例编号、现象分类、一句话描述、发生时间。
5. 点击“开始采集”，观察进度条与逐项状态。
6. 采集完成，工具给出摘要结论与缺失项清单，生成标准包。
7. 包保存到本地并按配置上传（共享目录或服务器），生成可复制的包路径/编号，贴进工单。
8. 研发拿到包，先看 HTML 摘要定位方向，再按需要深入原始数据。

> **提示**　设计约束：采集必须在“用户还记得细节”的几分钟内完成。因此表单字段要少、默认值要合理、支持先采集后补填，且任何一项采集失败都不能让整个流程中断。


## 4 采集内容需求


### 4.1 原则：以终为始

先明确研发拿到包之后要回答哪些问题，再倒推需要采集什么。这是判断“某个日志该不该采”的唯一标准。

**表 4-1 从研发问题倒推采集项**

| 研发需要回答的问题 | 必须依赖的数据 |
| --- | --- |
| 问题发生在什么时间点？之前系统做了什么？ | 事件日志时间线、崩溃记录、更新与驱动安装记录、开关机记录 |
| 是硬件问题还是软件问题？ | WHEA 硬件错误、BugCheck 代码、SMART、温度与降频记录、转储 |
| 是哪个驱动或设备导致的？ | 驱动清单与版本、问题设备、驱动安装历史、设备树快照 |
| 是不是环境被改过？（装了软件、换了驱动、改了策略） | 补丁列表、已安装程序、驱动安装事件、电源计划、安全软件与虚拟化状态 |
| 这台机器的配置和批次是什么？ | SN、机型、BIOS/EC 版本、CPU/内存/存储/屏幕/电池规格 |
| 测试条件是否影响了结果？ | AC/DC 状态、电量、性能采样、外设、环境温度、采集档位 |
| 能不能复现？复现需要什么条件？ | 测试用例、复现步骤、现象描述、是否可复现、现场截图 |

### 4.15 采集档位定义

一个档位打天下必然失败：要么太慢太重，要么漏关键信息。建议三档，默认标准档。

**表 4-15 采集档位**

| 档位 | 目标耗时 | 目标体积 | 包含内容 | 适用场景 |
| --- | --- | --- | --- | --- |
| 快速 | ≤ 60 秒 | ≤ 30 MB | 系统基线、硬件摘要、最近 24 小时关键事件、问题设备、电源与电池快照、存储健康 | 现场初判、批量抽检、低配机器 |

## 7 输出物规范

输出物的规范性直接决定研发的消费效率。同样内容，结构混乱的包会让研发多花几十分钟找文件。


### 7.1 命名规则

包名格式：SN_用例编号_采集时间_场景_档位.zip。时间使用 24 小时制且带时区，避免跨时区误读。

```
SN1234567_TC-WIFI-0042_20261106-133500_网络_标准.zip
SN1234567_TC-BSOD-0007_20261106-091500_蓝屏_深度_2of2.zip
```


### 7.2 目录结构

一级目录用两位数字前缀强制排序，研发按编号顺序看即可，不依赖文件名猜测。目录名与内容一一对应，新增内容只能放进既有目录或新增编号，不允许随手建目录。

### 7.4 摘要报告（HTML）要素

摘要决定研发“先看哪里”。它必须能在 3 分钟内给出方向，而不是把原始数据换个格式再堆一遍。

- 页头：机型、SN、OS、BIOS/EC、采集时间、场景、档位、采集人。
- 自动标记的异常摘要：蓝屏与停止代码、异常关机、硬件错误（WHEA）、显示驱动超时、问题设备、磁盘告警、电池健康异常、异常降频。
- 关键事件时间线：按时间排序，可展开查看参数原文；标注崩溃点与重启点。
- 硬件健康卡片：电池健康度、磁盘 SMART 关键项、内存容量、温度区间。
- 环境风险提示：开启了虚拟化/内存完整性、存在未签名或过旧驱动、非官方 BIOS、第三方安全软件。
- 缺失项与原因：哪些没采到、为什么（权限不足/超时/系统不支持），避免研发误以为“没有问题”。
- 免责与隐私声明：数据用途、脱敏说明、联系人与反馈渠道。


### 7.5 交付方式

- 本地保存到可配置目录，采集完成后自动打开所在文件夹并显示包名，便于复制粘贴到工单。
- 共享目录：配置 UNC 路径，直接写入并校验可读性。
- 服务器上传：HTTP(S) 接口，带采集 ID 与校验值，支持断点续传与失败重试；上传结果回写到界面与 manifest。
- 所有通道失败时，本地包必须完整保留，不能因为上传失败而丢弃数据。


## 8 隐私、安全与合规

日志包天然包含大量个人信息，且往往要跨部门流转。合规不是事后补丁，而是采集范围与默认值的设计约束。


### 8.1 数据分级与默认处理

**表 8-1 数据分级与默认处理**

| 数据项 | 敏感级别 | 默认处理 |
| --- | --- | --- |
| 机型、BIOS/EC 版本、硬件规格 | 内部 | 采集 |
| 设备序列号（SN） | 内部（可关联到人） | 采集，可按配置替换为哈希值 |
| 用户名、账号、域、邮箱 | 个人信息 | 脱敏（保留角色标记，如 user01） |
| 文件路径、文档名、最近打开记录 | 个人信息 | 保留盘符与目录结构，掩码用户名部分 |
| Wi-Fi SSID、BSSID、密码 | 敏感 | SSID 可掩码；密码一律不采集 |
| IP 地址、MAC 地址 | 个人信息 | 保留网段，主机位掩码 |
| 登录与安全审核日志 | 敏感 | 默认不采，需显式勾选并记录操作人 |
| 内存转储内容 | 敏感（可能含明文凭据） | 默认不采；勾选时提示风险，包可加密 |
| 截图、录屏 | 敏感（可能含屏幕内容） | 默认不采；采集时提示遮挡敏感区域 |
| 剪贴板、浏览器历史、聊天记录、文档正文 | 隐私 | 不采集 |


### 8.2 脱敏规则

- 白名单优先：只采集清单内的数据，而不是先全量再删减。
- 脱敏在打包前完成，落盘即脱敏，避免中间产物泄露。
- 正则规则集中管理、可配置、有版本号，并写入 manifest。
- 保留“可逆性”选项仅用于内部深度分析，且必须加密并限制访问。
- 提供脱敏自检：打包前扫描包内文件，命中敏感模式则告警并给出定位。


### 8.3 告知与授权

- 首次运行时展示采集范围与用途说明，用户确认后方可使用；说明文本可随配置更新。
- 采集界面常驻提示“本次将采集哪些类别”，支持逐类查看明细。
- 每次采集记录操作人、时间、采集项，形成可审计记录。
- 若涉及出境或对外提供，需在工具层强制开启最强脱敏档。


### 8.4 安全底线

- 不采集任何口令、密钥、证书私钥、浏览器 Cookie。
- 不在包内写入可执行脚本（避免包本身成为攻击载体）。
- 上传使用公司认可的通道，禁止明文 HTTP 传输敏感数据。
- 工具不提供远程执行、远程配置下发能力。
